# Security Policy and Threat Model

## Overview

SurakshaSutra is a learner-owned digital-safety application deployed as an Angular browser client behind nginx and a NestJS API on Google Compute Engine. Firebase Authentication is the identity authority; the API is the only trusted path to the named Firestore database. Vertex AI is restricted to adapting approved explanations and extracting teach-back claims. Deterministic application code owns authorization, profile isolation, learner-state transitions, misconceptions, routing, scheduling, and analytics.

The protected assets are Firebase identities and ID tokens; household/profile membership; constitutions and consent; learner observations, state, misconceptions, review schedules, analytics, and evidence; model requests and outputs; evaluator controls; deployment credentials; and service availability. Raw teach-back text is processed but not retained. P1 uploads, production voice processing, payments, institutional tenancy, and native clients are out of scope because they are not exposed in P0.

Security reports should avoid learner data and credentials. A report should identify the affected route or component, the expected security property, reproducible steps using synthetic data, and impact. Never include live `.env` values, Firebase ID tokens, service-account material, API keys, private prompts, or another learner's data.

## Threat Model, Trust Boundaries, and Assumptions

The primary trust boundaries are:

1. The untrusted browser and internet cross TLS/nginx into the API. Browser state, route parameters, Firebase claims supplied by the client, response timing, uploaded text, and headers are attacker-controlled.
2. Firebase Authentication establishes a subject, but household membership and profile ownership are reloaded and enforced by the API for every scoped operation. Possession of one valid household token must not grant access to a different household or profile.
3. The API crosses into Firestore using a dedicated least-privilege runtime service account. Direct browser Firestore access is not trusted. Tenant, household, and profile identifiers are part of every stored authorization boundary.
4. Approved curriculum and learner state cross into Vertex AI. Model output is untrusted data: it must pass strict schema, allowlist, size, and safety checks before display or state use. The model cannot write mastery or authorize actions.
5. Persisted events cross into derived analytics and optional BigQuery export. Metrics must be calculated from accepted stored events and remain household/profile scoped; export failure cannot mutate or block learning state.
6. Deployment secrets cross from the ignored mode-`0600` `.env` into the API container. They must never enter images, Git, frontend bundles, public configuration, logs, traces, evidence, errors, or exports. Secret Manager is intentionally outside this design under the current operator policy.
7. Evaluator reset and forced-fallback controls cross an elevated authorization boundary. They are accepted only for the configured evaluator Firebase identity/claim and must be auditable and unavailable to ordinary household users.

Assumptions: Google-managed Firebase, Firestore, Vertex, and TLS services enforce their documented controls; the GCE host and Docker daemon are operator-administered; the production host resolves to the intended VM; the runtime service account retains only the documented roles; curriculum files and container images come from the reviewed repository; and evaluator credentials are rotated after submission. A compromised host or authorized cloud administrator is outside application-layer isolation guarantees, but blast radius is limited through the runtime identity, API restrictions, `.env` permissions, loopback-only containers, and non-root API runtime.

## Attack Surface, Mitigations, and Attacker Stories

| Surface                       | Attacker story and impact                                                                                                                                                                     | Required mitigation                                                                                                                                                                                                                                       |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Authentication                | An attacker submits a forged, expired, replayed, or wrong-project Firebase token to impersonate a learner.                                                                                    | Verify signature, issuer, audience, expiry, and revocation-sensitive identity server-side; never trust client claims alone; use short-lived ID tokens and TLS.                                                                                            |
| Profile isolation             | An authenticated household member changes a profile or household ID to read or overwrite another learner's constitution, state, analytics, or evidence.                                       | Load current membership on every request, verify stored object ownership, scope all queries/documents by household and profile, deny mismatches, and regression-test horizontal access attempts.                                                          |
| Elevated controls             | A normal user calls reset or forces model failure, deleting evaluator state or manipulating evidence.                                                                                         | Require the configured evaluator UID or verified evaluator role, audit the operation, use idempotency, and expose no global kill switch.                                                                                                                  |
| Input and API abuse           | An attacker sends oversized JSON, unknown fields, duplicate submissions, invalid confidence/timing values, path confusion, or request floods to corrupt state or exhaust resources.           | Body limits, strict DTO/Zod schemas, bounded values, global safe errors, explicit methods/CORS, per-class rate limits, idempotency keys, Firestore transactions, request trace IDs, and deterministic conflict handling.                                  |
| Stored/reflected XSS          | Learner text or model output injects markup/script into the Angular UI or Evidence Drawer.                                                                                                    | Treat output as text, avoid unsafe HTML APIs, reject HTML/script patterns, use Angular escaping plus restrictive CSP, and never reflect secrets or raw provider errors.                                                                                   |
| Prompt injection/model misuse | Teach-back text asks the model to ignore policy, reveal prompts, invent rubric IDs, or generate operational scam instructions.                                                                | Delimit untrusted input, use narrow system templates and structured JSON, allowlist concept/rubric/invariant IDs, cap input/output, safety-scan before display, reject invalid output, and use visibly labelled curated fallback.                         |
| Fabricated learning state     | A model response or client-supplied score overwrites mastery, misconception severity, route, or review timing.                                                                                | Only deterministic versioned engine functions consume accepted observations; record state before/after, source events, formula version, and reason; model outputs never contain writable mastery.                                                         |
| Scenario safety               | Curated or generated training content includes active links, real organizations, phone numbers, credentials, credential requests, executable instructions, or realistic malicious operations. | P0 scenarios are curated, always show `TRAINING SIMULATION`, pass fail-closed safety validation, and use fictional, non-operational content and approved IDs only.                                                                                        |
| Firestore/data integrity      | Concurrency, partial writes, unscoped queries, or client access causes cross-tenant reads, lost updates, decorative analytics, or inconsistent evidence.                                      | API-only data access, least-privilege OAuth identity, named database, transactions/batches for observation/state/event/evidence, idempotency records, bounded query scopes, delete protection, and analytics derived from stored events.                  |
| Privacy and consent           | Voice, teach-back content, personalization signals, or reminders are processed after consent withdrawal or retained unnecessarily.                                                            | P0 hides voice; do not retain raw teach-back; enforce per-profile consent before signal use; support inspect, correction, export, reset, and disable; keep independent histories and clear seeded/estimate labels.                                        |
| Vertex/Google APIs            | Provider timeout, quota failure, malicious output, endpoint substitution, or leaked API key breaks learning or exposes data.                                                                  | HTTPS fixed Google endpoints, environment-configured project/location/model, IP/API-restricted service-account-bound key, 12-second timeout, at most one transient retry, schema/safety validation, redaction, safe metadata only, and truthful fallback. |
| Secrets and logs              | `.env` values, tokens, credentials, prompts, learner text, or hidden reasoning leak through Git, images, errors, traces, or Evidence Drawer.                                                  | `.gitignore`/`.dockerignore`, mode `0600`, server-only injection, structured redaction, safe error envelopes, no raw body/token logging, public-config allowlist, and secret scanning before push/deploy.                                                 |
| Network/browser               | TLS stripping, framing, cross-origin requests, service-worker staleness, or open internal ports attacks sessions or serves stale code.                                                        | HTTPS redirect, HSTS, CSP, frame denial, explicit CORS, referrer/permissions headers, loopback-bound container ports, no-store app shell/runtime config, hashed assets, and health-gated rollout.                                                         |
| Supply chain/deployment       | A compromised dependency/action/image or incomplete rollout runs unreviewed code; a rollback restores incompatible state.                                                                     | Frozen pnpm lock, minimal/pinned runtime images, CI gates, reviewed diffs, non-root API, no-new-privileges, immutable release identifiers, health checks, retained previous image, and documented rollback without schema destruction.                    |
| Availability/cost             | Automated requests exhaust Vertex quota, Firestore operations, memory, or VM capacity.                                                                                                        | Separate auth/state/model rate limits, strict input/token/time bounds, fallback without model retries, health monitoring, request cancellation, bounded arrays/queries, and graceful analytics failure.                                                   |

## Severity Calibration (Critical, High, Medium, Low)

- **Critical:** unauthenticated or cross-tenant bulk learner-data access; production credential or service-account private-key exposure; arbitrary code execution on the production API/host; evaluator reset available without authorization; model output directly writing mastery at scale; or fabricated live-AI evidence in the evaluator journey.
- **High:** cross-profile read/write within a household; authentication bypass; prompt injection that exposes protected data/prompts or displays operational scam content; persistent XSS in a core journey; consent bypass for retained sensitive input; deterministic-state corruption; or an unusable production deployment without truthful fallback.
- **Medium:** meaningful denial of service or cost amplification; non-persistent reflected XSS requiring a logged-in victim; missing idempotency that duplicates observations; analytics leakage without raw learner content; evidence redaction failure limited to non-secret internal metadata; or accessibility/security control failure affecting a core evaluator step.
- **Low:** minor information disclosure without learner data or credentials; security-header weakness with no demonstrated protected impact; low-rate nuisance abuse; or defense-in-depth issues that do not cross identity, profile, consent, model-safety, state-integrity, or deployment boundaries.

Severity is reduced when exploitation requires an authorized owner acting only on their own profile and produces no broader confidentiality, integrity, safety, or availability impact. It is increased when the issue crosses household/profile boundaries, affects minors or consent, can fabricate learning/evidence, exposes operational scam content, or is reliable on the deployed evaluator path.
